# 模块地图与扩展指南

给"要动这个项目的人"看的一页纸：**东西在哪、数据怎么流、加功能该动哪几个文件**。

配套文档：[参数与版本管理](参数与版本管理.md)（版本怎么升、参数放哪层）。

---

## 一、分层

依赖方向**严格单向向下**，不允许下层反向依赖上层：

```
        ui/            界面：Compose 页面 + ViewModel（只做展示与交互编排）
         │
      data/repo/       业务编排：一次对话/一次提炼的完整流程
         │
 ┌───────┼────────┬──────────────┐
 │       │        │              │
data/db  remote/  core/memory/  media|tts|modules|pet
 存储     传输     纯计算          平台能力
 │       │        │              │
 └───────┴────────┴──────────────┘
         core/      基础：Result / JsonExt / 时间工具
```

三条硬规则：

1. **`core/` 不依赖 Android**（除时间工具外），因此可以纯 JVM 单测。
   `MemoryDecay`、`MemoryRecall`、`MemoryTextIndex`、`ExtractedMemory` 都是纯函数对象——
   这是记忆系统能被 207 个用例钉住的前提。
2. **`remote/` 只负责"把字节搬过去、把字节搬回来"**，不做业务判断。
   解析全部抽成纯函数（`ChatStreamParser`、`SearchResponseParser`），单独测。
3. **`ui/` 不直接碰网络或 SQL**，一律经 `AppContainer` 拿到的 repo / store。

### 2.1 导航：聊天 / 通讯录 / 聊天信息页

界面按微信分成三块，**职责不重叠**喵：

| 页面 | 管什么 | 入口 |
| --- | --- | --- |
| 主界面「聊天」 | **对话**列表 | 打开应用即是 |
| 「通讯录」 | **角色**列表（拼音分组 + 右侧索引） | 底部第二个标签 |
| 「聊天信息」 | **这一段对话** | 对话右上角「⋯」（不是下拉菜单） |
| 「角色资料」 | **这个人** | 通讯录点角色，或聊天信息页点头像 |

```
主界面（对话列表）
   ├─ 点一行 ──▶ 对话 ──▶ 右上角「⋯」──▶ 聊天信息页 ──▶ 点头像 ──▶ 角色资料页
   │                       │                                      │
   │                       ├─ 删除对话（隐藏）                    ├─ 发消息
   │                       ├─ 清空聊天记录（真删）                ├─ 编辑资料
   │                       └─ 收藏 / 模块 / 调试 / 记忆           ├─ 该角色记忆
   ├─ 长按一行 ──▶ 置顶 / 取消置顶、删除对话                       └─ 删除联系人
   ├─ 通讯录 ──▶ 点角色 ──▶ 角色资料页
   ├─ 收藏 / 记忆 / 设置
   └─ 搜索 / 模块 / 调试   （二级页，AppScreen）
```

**置顶**喵：长按主界面一行弹出操作菜单，可以置顶 / 取消置顶，也可以删除对话喵。
置顶的行底色比普通行更浅（浅色模式）／更亮（暗色模式），
底部标签栏取两者之间的那一档，三层明度依次递进，色值在 `ui/theme/Color.kt` 喵。

排序规则写在 `buildChatList` 里：**先按 `pinned`，再按最近活动**，
两级写在同一次 `sortedWith` 里喵。注意 `listVisible()` 里虽然也有
`ORDER BY pinned DESC`，但 `buildChatList` 末尾会在内存里重排，
**只靠 SQL 那句置顶不会生效**——置顶逻辑必须落在这个纯函数里喵。

`setPinned` 只改 `pinned` 一列、**不动 `updated_at`**：
置顶是"摆放"动作而不是"聊天"动作，顺手刷新活动时间的话，
取消置顶后它会假装刚聊过而窜到最前面喵。

### 2.3 发送管线：消息与后端彻底解绑

**发消息与生成是两件事**喵。用户按下发送的那一瞬间，消息就落库并上屏了——
界面立刻能看到、也能立刻继续发下一条，不管模型是不是正在生成喵。
生成由一条**独立的流水线**负责，消息只是"欠了它一轮"喵。

规则喵：
- 从**第一条**未被处理的消息起算一个 3 秒窗口，窗口内的消息算同一批一起注入喵
- 窗口关闭时若上一轮还在生成，就排队等它**生成完毕**（不是等打字机播完）喵
- 「前一轮处理完」＝生成完毕：打字机只是本地回放，让它挡住下一轮会让用户觉得"发了半天它不理我"喵

**为什么必须先落库再上屏**喵：早期是"先塞一条负数 id 的临时消息，落库后换成真 id"。
但 LazyColumn 的 key 因此从 `msg--123` 变成 `msg-42`，而 `animateItem()` 看到 key
消失又出现会当成「删了一条 + 插了一条」——Compose 的 `LazyLayoutItemAnimator` 会把
消失项放进 `disappearingItems`，用**独立的绘制层**在旧位置冻结一个淡出副本喵。
表现就是"融进背景、滑动时不动"喵。落库是本地 SQLite，几毫秒的事，用户察觉不到喵。

**三个容易写错的地方**（都踩过）喵：

1. `streamJob` 代表**整条流水线**而不是某一次生成，所以 `runOneBatch` 里绝不能
   `streamJob?.cancel()`——那等于把正在执行自己的协程掐掉，表现为发出去毫无反应喵
2. 判断"要不要开新流水线"不能看 `streamJob.isActive`：窗口恰好在流水线收尾时关闭的话，
   新调用会看到它仍 active 而直接返回，那一批就永远没人处理了喵。
   正确做法是**每次都起、用 `Mutex` 串行化**，后到的那条进去自己再看一眼喵
3. `ChatEvent.Finished` 里**不要**自己再起协程去跑下一批：流水线的 `while` 循环会接着跑，
   再起一条就变成两条线各跑一轮喵

**合并窗口的规则是纯状态机**（`SendBatchTracker`），它只记"窗口开没开、欠了几批"，
**不管计时**——3 秒的 `delay` 由 ViewModel 负责喵。把计时也塞进去的话，
这个纯函数就得依赖时钟，测试会变得又慢又不稳；分开之后那套分支能被逐条钉住喵。

表情包、红包、语音转文字**全都走同一条管线**（`onMessageQueued`），行为一致喵。

**面板收起要放在守卫之后**喵。这里踩过一个坑：`sendSticker` 开头原本是
`if (stream.generating) return`，而 `stickerPanelOpen = false` 写在它后面——
于是模型正在生成时点表情会**整个 return**，面板不收起、表情也发不出去喵。
现在生成守卫已经按"随时能发"的要求去掉了，但**顺序**这件事仍要记住：
任何"发送时要顺手做的事"（收面板、清输入框）都必须排在可能提前返回的判断之前喵。

发送时三个面板都收：输入框、表情面板、＋ 面板喵。发送是"我说完了"的动作，
面板继续摊着会挡住刚发出去的消息，也让人以为还没发出去喵。

### 2.4 返回键的层级

**全项目只在最外层注册一个 `BackHandler`**喵（`QingYuAppRoot`），
按 `decideBackAction` 的优先级逐层退，而不是每屏各注册一个喵。

每屏各注册一个的问题是：多层 `BackHandler` 靠组合顺序决定谁生效，
**一旦某屏忘记注册，返回键就会直接退出应用**——那正是"点返回就退出"的来源喵。
集中成一处之后，层级规则变成了一个纯函数，能被逐条钉住喵。

四层优先级（`BackAction`）喵，顺序对应"界面上盖在最上面的是什么"：

| 优先级 | 条件 | 动作 |
| --- | --- | --- |
| 1 | 有二级页面 | `POP_SCREEN` 退回上一层 |
| 2 | 对话覆盖层开着 | `CLOSE_CHAT` 关掉对话 |
| 3 | 不在「聊天」标签 | `GO_HOME_TAB` 回聊天标签 |
| 4 | 都退无可退 | `EXIT` 交还系统退出应用 |

**二级页面优先于对话覆盖层**这条最容易搞反喵：在对话里点「⋯」进聊天信息页时，
对话仍然开着（`persona` 非空），但屏幕上最上面的是聊天信息页——
这时按返回该退回对话，而不是把整段对话关掉喵。

导航栈是 `NavStack`（纯数据，有单测）喵，两条约定：
- **栈里只放二级页面**，`AppScreen.Home` 永远不入栈——它就是"栈空"本身喵。
  把 Home 也压进去会让"能不能退"变成"栈大小是不是 1"，到处要 ±1，很容易错喵
- 连续的同一个页面不重复入栈：连点两次同一项会触发两次导航，
  压两层的结果是"按一次返回没反应"，用户会以为卡了喵

`backToTabs()` 与 `back()` 的区别要分清喵：前者一路清空栈，后者只退一层。
用在"跳出当前钻取链路"的场景——例如从角色资料页点「发消息」进对话后，
退出对话该回主界面而不是回资料页喵。

---

**关键区分：「删除对话」≠「删除联系人」**喵

- `删除对话` = `conversations.hidden = 1`。**只从主界面移除**，
  角色、消息、记忆全都还在；从通讯录进去、或发出/收到新消息就自动回来喵
- `清空聊天记录` = `messages.deleteAll()`。**真的删消息，不可恢复**，角色保留喵
- `删除联系人` = `personas.delete()`。角色 + 对话 + 消息 + 记忆一起清喵

三者文案必须在点之前就说清楚，否则太容易误操作喵。

其余要点喵：

- 主界面只列**有对话、那段没被移除、且至少有一条消息**的角色。
  "没聊过"属于通讯录——进角色时 `latestOrCreate` 会建出空对话，
  若不滤掉，进去看一眼再退出就会平白多出一行喵
- 取"最近那段对话"**再看它是否被移除**，顺序不能反：
  先滤再挑的话，一段被删后更早的残留会顶上来，看起来就像删除没生效喵
- 切分与排序是纯函数 `buildChatList`，有单测钉住（含置顶优先、置顶组内排序、
  取消置顶后落回原位、以及"被移除的置顶对话照样不显示"）
- 通讯录分组用 `core/PinyinInitial`：拿系统 `Collator` 与 23 个锚点字做判定，
  **不内置拼音表**（省几十 KB），有单测钉住常见姓氏

> **改这一块要特别小心**：角色列表有两份来源——主界面的 `ChatViewModel.chatList`
> （只含可见对话）与通讯录的 `ChatViewModel.allPersonas`（含全部角色）。
> 早期"新建角色后看不到"的 bug 就是只有一边刷新造成的。
> 任何改动角色或对话的事件都必须 `refreshPersonas()` 让两边一起重算喵。

### 2.2 表情包 / 红包 / 语音 / 头像

**表情包的核心决定：名字与图片各占一半权重怎么落地**喵。

做法不是把两者拼成一段文字，而是**同时走两条既有通道**喵：
1. 消息的 `content` 写成表情的**名字**，于是它自然进入 `PromptBuilder.turns` 的文本流喵；
2. 图片本体作为一条普通 `Attachment` 挂上去，于是它自然进入既有的多模态 / 识图通道喵。

这样两边各占一半，而且**没有新增任何一条送模型的代码路径**——复用的都是早就验证过的逻辑喵。

有一条容易踩的耦合：`StickerRepository.send` 里附件的 `description` **必须留空**喵。
引擎的规则是"description 为空才送去识图"，所以喵：
- 主模型能看图 → 图片直接作为多模态内容发出，名字走 content，两半都在喵
- 主模型看不了图 → 识图模型描述这张表情，content 变成「名字 +（图片内容：…）」，仍是两半喵

若预填一句描述，它就永远不为空、识图永远不跑，第二条路径下模型就只剩名字可看喵。

**消息的结构化字段**喵：表情与红包都不是纯文本，所以 `messages` 加了
`kind`（text / sticker / red_packet）、`sticker_id`、`payload` 三列喵。
红包的金额与留言存在 `payload`（JSON）里，**界面画卡片读 payload、不解析 content**喵——
content 是给模型看的自然语言，措辞随时会改；让界面去正则匹配自己刚写下的那句话，
等于改一个字的文案就会让红包显示错喵。

**语音**喵：`media/AudioRecorder`（16 kHz 单声道 AAC）负责录，
`remote/TranscriptionClient`（OpenAI 兼容 `/audio/transcriptions`）负责转文字喵。

**接口地址与 Key 是识别与合成共用的，但模型名必须分开**喵：
`speech.model` 是合成模型（走 `/audio/speech`），`transcribeModel` 是识别模型
（走 `/audio/transcriptions`）喵。`tts-1` 是合成模型，拿去识别会被服务端直接拒掉，
所以设置页里这两个字段各自独立，**不要合并成一个**喵。

设置页的「语音」板块里，接口地址 / Key / 识别模型这三项**不受「朗读音色来源」影响、永远显示**喵。
原因是识别与合成是两件独立的事：识别服务于「按住说话」与通话，合成服务于朗读；
用户完全可能选系统语音朗读、却要用 AI 接口做识别喵。
把地址与 Key 关在"AI 语音"分支里，他就没法配识别了喵。

「测试语音识别」用 `media/SilentWav` 造一段 0.2 秒静音去探活：只验证
"地址 + Key + 模型名能不能被接受"，静音转不出文字是**成功**而不是失败喵。
这段 WAV 头是手写的 44 字节，字段写错时服务端只会回一句笼统的"格式不支持"，
所以有单测逐字段钉住（尤其是小端与两个长度字段的一致性）喵。

**通话**是**半双工一轮一轮**的：按住说话 → 转文字 → 发给角色 → 回复用语音念出来喵。
不做全双工是权衡的结果：全双工要回声消除与实时音频流，而"和角色打电话"
本来就是一句一句轮着说的，半双工复用了三条已验证的链路，出错也有明确落点喵。

通话中的回复**无条件念出来**，不看「启用朗读 / 自动朗读回复」这两个开关喵。
那两个开关是给聊天页的（那里朗读是可选的附加能力）；通话页的全部意义就是
"用嘴说、用耳朵听"，若不念，用户说完只会看到屏幕上一行字，通话等于断了喵。
`inCall` 由通话屏的 `DisposableEffect` 置位与清除，返回键与挂断都会走到清除喵。

**红包**是**纯虚拟**的：无充值、无支付、不接真实货币，金额由用户自己填喵。
它做的事只有一件——把"我给你发了多少钱"作为一句话送进上下文喵。
`MAX_AMOUNT` 不是防作弊（本来就虚拟），是防手滑输入天文数字让角色反应失真喵。

**头像**喵：`media/AvatarStore` 与 `ImageStore` 分开，因为生命周期完全不同——
聊天图片属于某条消息（删消息就该删图），头像属于**角色**（换头像删旧的、删角色删头像）喵。
混在一个目录里会让 `ImageStore.pruneOrphans` 把头像当孤儿误删喵。
`personas.avatar_image` 存**文件名**而不是绝对路径：私有目录的绝对路径会随安装位置变化，
备份恢复到另一台机器就失效了喵。

头像有图与 emoji 两条路并存，显示统一走 `PersonaAvatar(persona = …)` 重载，
**不要**在各处自己判断该画图还是画字——那样迟早漏掉一两处、出现同一角色两个样子喵。

**输入行的四格**是固定的：语音 | 输入框 | 表情 | ＋喵。
顺序不是随意的：语音与表情都是"另一种表达方式"，紧贴输入框两侧，
手指从输入框出发左右各挪一格就能碰到；＋ 收纳的是"别的功能"（联网 / 图片 / 通话 / 红包 / 朗读），
都不属于"说话"本身喵。有内容可发时 ＋ 让位给发送键——打完字最想点的就是发送喵。

## 三、一次对话发生了什么（数据流）

这是全项目最长的链路，读懂它，其余都是它的子集。

```
用户点发送
   │
   ▼
ChatViewModel.send()
   │
   ▼
ChatEngine.generate()                                  ← data/repo/ChatEngine.kt
   │
   ├─ 1. 落库用户消息（Stores.MessageStore）
   │
   ├─ 2. 联网（可选）：SearchClient → SearchResponseParser → List<SearchHit>
   │
   ├─ 3. 记忆准备：MemoryDirector.prepare()             ← 全本地、确定性
   │        ├─ advanceTurn()            推进轮次
   │        ├─ applyDecay()             按天衰减；跌破剪枝阈值就地压成残影
   │        ├─ recallFor()              粗召回 → 多因子打分 → 冷却/淡忘/概率 → 唤醒
   │        └─ markRecalled()           给唤醒的刷新冷却起点
   │
   ├─ 4. PromptBuilder.turns()          人设 + 记忆 + 历史 + 联网资料 → 请求体
   │
   ├─ 5. PromptRefiner.refine()（可选）  小模型润色；超时/异常即用原生提示词
   │
   ├─ 6. ChatClient.stream()            SSE 传输
   │        └─ ChatStreamParser        逐 chunk 解析（在此拦住 JSON null 噪音）
   │
   ├─ 7. BurstAccumulator              按空行拆成多条短消息，每段只落库一次
   │
   ├─ 8. 落库助手消息
   │
   └─ 9. 收尾（异步、不阻塞回复）
            ├─ MemoryExtractionService.launchAsync()      提炼新记忆
            └─ MemoryExtractionService.launchPruneCompression()  优化剪枝残影
```

**关键设计：第 9 步用 `AppContainer.appScope` 而不是调用方的协程。**
用户可能一发完消息就退出聊天页，但"替用户记住这件事"不该跟着界面一起消失。

## 四、扩展指南：加功能该动哪

### 4.1 加一个设置项

见[参数与版本管理 §4.1](参数与版本管理.md)——四处齐改，漏一处就静默失效。

**参数要挂「?」说明**：`ui/settings/HelpTexts.kt` 里加一条 `HelpContent`，
然后把它传给控件的 `help =` 参数。共享控件已经内置支持，不必自己画问号：

| 控件 | 写法 |
| --- | --- |
| `SwitchRow` / `SliderRow` | 多传一个 `help = HelpTexts.xxx` |
| 输入框 | `label = { LabelWithHelp("标签", HelpTexts.xxx) }` |
| 整组小标题 | `RowLabelWithHelp(label = "…", content = HelpTexts.xxx)` |
| 自定义布局 | 直接放 `HelpDot(content = HelpTexts.xxx)` |

说明按「用法 / 调整影响 / 建议参数」三段写，三段都可留空、留空的段不会渲染。
三段全空时问号不显示，所以可以无条件挂上。

> 「调整影响」这一段最值得花时间：用户看得懂"这是什么"，但通常不知道
> "调大了会怎样"。写清后果比解释原理有用。

### 4.2 加一张表 / 一个 Store

1. `DbHelper.createXxx(db)` 建表（含索引），并在 `onCreate` 里调用
2. `Db.VERSION +1`，在 `onUpgrade` 补一个 `if (oldVersion < N)` 分支，**并让 `onCreate` 与
   `onUpgrade` 建出完全一致的结构**
3. `Stores.kt` 里加 `XxxStore`，在 `QingYuDatabase` 上暴露为属性
4. 若表是给记忆用的，考虑是否需要在升级时**回填**（参考 `backfillMemoryIndex`）
5. 实体加到 `data/Models.kt`，配上 `toValues()` / `toXxx()` 双向映射

> 反序列化（`toXxx`）必须容忍缺列与 `null`，因为老库升级上来的行可能是默认值。

### 4.3 加一个页面

1. `ui/vm/XxxViewModel.kt`：`AndroidViewModel` + `AppContainer.get(application)` +
   `companion object { fun factory(application) }`（照抄 `ShellViewModel`）
2. `ui/vm/XxxUiState.kt`（简单的可直接写进 ViewModel 文件）
3. `ui/xxx/XxxScreen.kt`：只读 `state`、只调 `viewModel.xxx()`，不碰网络与 SQL
4. 若要成为底部标签 → `QingYuAppRoot.kt` 的 `HomeTab` 加枚举 + `when` 分支
5. 若是二级页 → `ui/vm/ShellViewModel.kt` 的 `AppScreen` 加 `data object` + `navigate()`

### 4.4 加一类外部能力（新的"另一个 OpenAI 兼容接口"）

项目已有识图 / 语音 / 搜索三例，第四例照这个形状做：

1. `data/ApiConfig.kt` 加路径常量与地址补全分支
2. `remote/XxxClient.kt`：只做传输，鉴权用统一的 Bearer
3. `remote/XxxParser.kt`：**把所有解析抽成纯函数**（这是能被测试的前提）
4. `remote/XxxPayload.kt`：请求体构造，也抽成纯函数
5. `AppContainer` 里装配
6. `Settings` 加配置（四处齐改）+ 设置页加"测试"按钮
7. `app/src/test/` 补解析与请求体的用例——**这类"输入不受我们控制"的地方必须有测试**

### 4.5 加一种记忆类型

1. `data/Models.kt` 的 `MemoryCategory` 枚举加常量（**枚举名会落库**，之后不能改名）
2. `core/memory/MemoryDecay.kt` 若涉及衰减/唤醒差异 → 加系数并在 `MemoryDecayTest` 钉一条
3. `core/memory/MemoryRecall.kt` 若涉及召回 → 改 `RecallConfig` 或候选池过滤
4. `MemoryExtractionService.INSTRUCTION` 里告诉模型何时产出该类型

6. 补测试

### 4.6 给 JS 模块加一个宿主 API

1. `modules/ModuleManager.kt` 里注册 `qingyu.xxx`
2. **必须走白名单接口**：没有网络、没有文件、没有反射、拿不到 Context——
   沙箱是结构性的，不是靠运行时检查
3. 单次运行有 2 秒与指令数上限，新 API 若是耗时的，自己也要有界
4. `SimpleJsEngineTest` 补用例

## 五、约定（写新代码时照这个来）

- **注释**：每个文件、每个类/对象顶部一段 KDoc，说"它是什么、为什么这样设计"，
  而不只是复述代码。**为什么这么写要写进注释**（例：为什么 `NEVER_RECALLED_TURN` 是 `-100`
  而不是 `0`），这是这个项目注释的主要价值。
- **命名**：`XxxStore`（DAO）、`XxxClient`（传输）、`XxxParser`（纯函数解析）、
  `XxxViewModel` + `XxxUiState`（界面）、`XxxConfig`（参数集合）。
- **纯函数优先**：能写成纯函数的（解析、打分、衰减、拆条）就不要掺协程与 Android 依赖，
  这样才测得动。
- **确定性**：记忆的"想不想得起来"必须可复现——随机数按 `(记忆 id, 轮次)` 播种
  （见 `MemoryRecall.Dice`），同输入永远同结果。**不要引入全局随机源。**
- **失败要静默降级**：润色超时 → 用原生提示词；AI 语音失败 → 回退系统 TTS；
  提炼失败 → 忽略。**这些能力都是纯收益项，不值得拖住主流程。**
- **测试取向**：只给"输入不受控制"或"错了不报错、只会静默失效"的地方写测试，
  不追求覆盖率数字。README「三处静默失效的陷阱」一节列了具体清单。
