# 参数与版本管理

这份文档回答两件事：**版本号写在哪、怎么升**，以及**各类参数放在哪一层、改哪个**。

原则只有一条：**每个参数只有一个真源（single source of truth）**。
同一件事不允许在两个文件里各写一份默认值——否则改一处、漏一处，就会出现
"设置页显示 8 条，实际注入 6 条"这种不报错但行为不对的故障。

---

## 一、版本号：一共四种，各管一段

| 版本 | 真源（唯一） | 当前值 | 谁在用 |
| --- | --- | --- | --- |
| **应用版本** | [`app/build.gradle.kts`](../app/build.gradle.kts) `defaultConfig.versionCode / versionName` | `11` / `"1.2.2"` | 系统安装/升级判定；设置页"关于"显示 |
| **数据库 schema** | [`DbHelper.kt`](../app/src/main/java/com/qingyu/app/data/db/DbHelper.kt) `Db.VERSION` | `8` | `SQLiteOpenHelper` 的 `onCreate` / `onUpgrade` |
| **导入导出格式** | [`ChatArchive.kt`](../app/src/main/java/com/qingyu/app/data/archive/ChatArchive.kt) `ChatArchive.SCHEMA` | `"qingyu.chat.v1"` | 导出的 JSON，以及导入时的格式识别 |
| **依赖版本** | [`gradle/libs.versions.toml`](../gradle/libs.versions.toml) | AGP 9.3 / Kotlin 2.2.10 / Compose BOM 2026.02.01 | Gradle 解析依赖 |

### 1.1 应用版本（versionCode / versionName）

`versionCode` 是**整数**，只能单调递增——它是 Android 判断"这是不是一次升级"的唯一依据。
`versionName` 是给人和设置页看的字符串，随便写，不参与任何判定。

```kotlin
// app/build.gradle.kts
defaultConfig {
    versionCode = 1        // 每次发版 +1，永不回退
    versionName = "1.0.0"  // 语义化版本，展示用
}
```

**不要在 Kotlin 代码里再写一份版本号字符串。** 设置页显示版本走的是系统查询：

```kotlin
// ui/vm/SettingsViewModel.kt —— 构造时读一次，之后不再变
application.packageManager
    .getPackageInfo(application.packageName, 0)
    .versionName
```

这样 Gradle 里改了 `versionName`，关于页立刻跟着变，不存在两处不同步。

`debug` 变体额外加了 `applicationIdSuffix = ".debug"`（包名变成 `com.qingyu.app.debug`），
所以调试包和正式包可以同时装在一台机器上，互不覆盖。

### 1.2 数据库 schema 版本

```kotlin
object Db {
    const val NAME = "qingyu.db"
    const val VERSION = 4
}
```

**升级规则（务必遵守）：**

1. `VERSION` 只能 `+1`，不能跳号、不能回退。
2. 每加一个版本，在 `onUpgrade` 里补一个 `if (oldVersion < N) { ... }` 分支，
   **增量写**，不要改写历史分支——用户可能从 v1 一路升到 v4，每一档都要能过。
3. 只做"加列加表"，不做删列改类型（SQLite 的 `ALTER TABLE` 能力很有限）。
   真要删列，走"建新表 → 拷数据 → 换名"。
4. 新列必须有 `NOT NULL DEFAULT <合理值>`。默认值选错会造成**静默的数据体验事故**，
   历史上有两个真实案例写在代码注释里：
   - `last_recalled_turn` 默认补 `-100`（`NEVER_RECALLED_TURN`）而不是 `0`——
     默认 `0` 会让所有老记忆升级后立刻被判"刚提过"，集体冷却 20 轮，表现为"升级完记忆全没了"。
   - `pruned` 老数据补 `0`（当未剪枝处理），不能用 `1`。
5. 如果新表需要**回填**已有数据（例如倒排索引 `memory_terms`），
   必须在 `onUpgrade` 里显式调用回填函数（见 `backfillMemoryIndex`），
   否则症状是"功能在，但一条都匹配不上"。
6. 用户机器上的库下载不到、只能就地升级——`onCreate` 和 `onUpgrade` **两条路径都要能建出
   完全一致的表结构**。加表/加列时两个函数都要改，漏一个就会出现"新装用户正常、
   升级用户崩溃"。

版本历史（写在 `Db.VERSION` 的 KDoc 里同步维护）：

| 版本 | 内容 |
| --- | --- |
| v1 | 初版：personas / conversations / messages / favorites / memories |
| v2 | messages 加 `search_json`、`has_image`；新增 attachments 表 |
| v3 | memories 加三元组与遗忘曲线状态；新增 memory_terms（倒排索引）、memory_state（轮次） |
| v4 | memories 加剪枝列：`pruned` / `original_content` / `prune_enhanced` |
| v5 | 倒排索引打分口径变更，升级时按新口径回填权重 |
| v6 | **一个角色只剩一个对话**：升级时每个角色只保留最近活动的对话，其余连同消息/附件/轮次一并删除 |
| v7 | conversations 加 `hidden` 列：对话可从主界面移除（角色与消息都保留，发消息即回来） |
| v8 | personas 加 `avatar_image`（自定义头像文件名）；messages 加 `kind` / `sticker_id` / `payload`（表情包与红包的结构化字段）；新增 stickers 表 |

> v6 的取舍：界面改成"角色即会话"后，同一角色的旧对话再无入口，
> 留着只会白占空间。**不合并多个对话的消息**——合并会把不同时期的话题揉在一起、
> 时间线错乱，读起来比丢掉更糟。详见 `DbHelper.collapseConversationsPerPersona`。

> v8 的取舍：表情与红包都是**非纯文本**消息，所以单列 `kind` 而不是在 content 里加前缀标记。
> 前缀会污染送给模型的文本，而且用户手打的字里出现同样的前缀就会误判。
> 红包金额存 `payload`（JSON）而**不是**从 content 反解——content 是给模型看的自然语言，
> 界面去正则匹配自己刚写下的那句话，改一个字的文案就会让卡片显示错。

### 1.3 导入导出格式版本

```kotlin
// data/archive/ChatArchive.kt
const val SCHEMA = "qingyu.chat.v1"
```

导出 JSON 顶层带这个字段，导入时据此判断兼容性。
**改动导出字段 = 改 schema 字符串**（`qingyu.chat.v2`），并且导入器要同时认 v1 和 v2，
否则老备份就废了。导入端还要兼容**裸数组**那种早期写法（顶层直接是消息数组、没有 schema 字段），
改字段前先确认不会把这类老备份读废。

### 1.4 依赖版本

统一写在 [`gradle/libs.versions.toml`](../gradle/libs.versions.toml)（Gradle 版本目录），
`build.gradle.kts` 里只引别名（`libs.androidx.core.ktx`），**不写版本号**。

**AGP 9 的注意点**：AGP 9 已内置 Kotlin 支持，顶层 `build.gradle.kts` 里
`kotlin-android` 插件已 `apply false`，**不要再应用它**，否则报"扩展重名"。
目前只应用 `android-application` 与 `kotlin-compose`。

### 1.5 签名

`keystore.properties`（仓库根）保存四项：`storeFile` / `storePassword` / `keyAlias` / `keyPassword`。
文件不存在时构建自动退化为**未签名包**，所以别人 clone 下来也能直接编译——
这是有意设计，不要在代码里改成"缺文件就报错"。

正式上架前把该文件加进 `.gitignore` 并换成自己的 keystore。

## 二、参数：一共四层，按"谁来决定"分层

判断一个参数该放哪层，只问一句：**它需要在不重新编译的情况下改变吗？**

| 层 | 位置 | 变化时机 | 典型例子 |
| --- | --- | --- | --- |
| **L1 构建期常量** | Gradle / `const val` | 改代码重新编译 | `compileSdk`、`Db.VERSION`、接口路径片段 |
| **L2 领域常量** | 各模块 `companion object` | 改代码重新编译，但只影响一个领域 | 衰减系数、冷却轮数、索引词上限 |
| **L3 用户可调** | [`data/Settings.kt`](../app/src/main/java/com/qingyu/app/data/Settings.kt) `AppSettings` | 用户在设置页随时改，落 SharedPreferences | 温度、注入条数、主题、API Key |
| **L4 运行时派生** | `MemoryDirector.configFor()` 等翻译层 | 每次调用由 L3 算出来 | `RecallConfig`（从 AppSettings 夹紧后的值） |

**关键约定：L3 到 L4 之间必须有夹紧（coerce）。**
用户能把滑杆拉爆，或手改 SharedPreferences；下层不许假设拿到的值合法。
例如 `MemoryDirector.configFor`：

```kotlin
fun configFor(settings: AppSettings): RecallConfig = RecallConfig(
    limit = settings.memoryInjectLimit.coerceIn(1, MAX_INJECT_LIMIT),  // 夹紧
    cooldownTurns = settings.memoryCooldownTurns.coerceAtLeast(0),      // 夹紧
    ...
)
```

夹紧只写在这一处，下游就不必各自防御。

## 三、重要参数索引

改之前先来这张表里找位置。**加粗**的是改动会明显影响行为、需要配套测试的。

### 3.1 记忆：遗忘曲线与唤醒

真源：[`core/memory/MemoryDecay.kt`](../app/src/main/java/com/qingyu/app/core/memory/MemoryDecay.kt)

| 参数 | 默认 | 作用 |
| --- | --- | --- |
| `LAMBDA_PER_DAY_NORMAL` | `0.10` | 普通记忆按天衰减系数（半衰期约一周） |
| `LAMBDA_PER_DAY_USER_EDITED` | `0.05` | 用户手改过的记忆，衰减减半 |
| `LAMBDA_NORMAL` / `LAMBDA_USER_EDITED` | `0.05` / `0.025` | **回合制版**，仅测试与向后兼容在用 |
| `COOLDOWN_TURNS` | `20` | 唤醒后强制屏蔽轮数，避免反复念叨同一个梗 |
| `VIVIDNESS_FLOOR` | `0.2` | 鲜活度低于此值不再参与唤醒 |
| `PRUNE_VIVIDNESS_THRESHOLD` | `0.05` | 跌破此值触发剪枝（压成残影） |
| `REAWAKEN_VIVIDNESS` | `0.5` | 残影被唤醒后恢复到的鲜活度 |
| `BASE_PROBABILITY` / `_USER_EDITED` | `0.1` / `0.25` | 唤醒概率基数 |
| `MAX_PROBABILITY` | `0.5` | 唤醒概率上限 |
| `EMOTION_COEFFICIENT` | `0.2` | 情绪权重对唤醒概率的加成系数 |
| `VIVIDNESS_COEFFICIENT` | `0.1` | 鲜活度对唤醒概率的加成系数 |
| `NEVER_RECALLED_TURN` | `-100` | "从未唤醒"哨兵值，**不能改成 0**（见 §1.2） |

综合得分权重（`compositeScore`，决定候选排序）：
相似度 `0.30` / 重要度 `0.25` / 鲜活度 `0.20` / 情绪 `0.15` / 间隔成熟度 `0.10`。
五者之和应为 `1.0`，改权重时保持这个约束，否则分数不再落在 `0..1`。

### 3.4 存储

| 参数 | 位置 | 默认 | 作用 |

## 四、新增一个参数：照抄这份清单

### 4.1 如果是"用户可调"参数（最常见）

必须**同时**改 [`data/Settings.kt`](../app/src/main/java/com/qingyu/app/data/Settings.kt) 的四处，
少一处就会出现"改了不生效"或"重启后丢失"：

1. `data class AppSettings` 加字段 + 默认值（**KDoc 写清楚单位与含义**）
2. `private companion object` 加 `KEY_XXX = "..."` 常量
3. `load()` 里加 `xxx = prefs.getXxx(KEY_XXX, defaults.xxx)`
4. `persist()` 里加 `.putXxx(KEY_XXX, settings.xxx)`

然后按需：
5. 若要在设置页可改 → [`ui/settings/SettingsScreen.kt`](../app/src/main/java/com/qingyu/app/ui/settings/SettingsScreen.kt)
   对应折叠分组里加 `SwitchRow` / `SliderRow` / `OutlinedTextField`
6. 若会影响检索 → 在 `MemoryDirector.configFor` 里翻译成 `RecallConfig` 字段并**夹紧**
7. 若有非平凡逻辑（阈值、分支）→ 在 `app/src/test/` 下补单元测试

### 4.2 如果是"领域常量"

放在**使用它的那个模块**的 `companion object` 里，不要塞进全局配置大对象：

- 好处：改衰减系数不用翻过整张全局表；模块自洽，删模块不留孤儿常量
- 要求：`const val` 上方写一句 KDoc，说明**单位和为什么是这个值**
- 例外：跨 2 个以上模块共用的才考虑上提

### 4.3 如果改了会影响行为的常量

按 README「测试覆盖」一节的取向：**"输入不受我们控制"或"错了不报错只会静默失效"的地方必须有测试**。
目前 `MemoryDecayTest` 就是每个系数钉一条用例——加系数请顺手加用例。

## 五、发版 checklist

```
[ ] app/build.gradle.kts: versionCode +1（必须），versionName 更新
[ ] Db.VERSION 若动过 schema：已 +1，且 onCreate 与 onUpgrade 两条路径都改了
[ ] 新增列都有合理的 NOT NULL DEFAULT（想清楚老数据升级后的表现）
[ ] 需要回填的表：onUpgrade 里已调用回填
[ ] KEY_* 没有改动既有字符串（只新增）
[ ] AppSettings 新字段四处齐全（字段/KEY/load/persist）
[ ] 导出格式若变：SCHEMA 已升版，且导入器兼容旧版
[ ] ./gradlew.bat :app:testDebugUnitTest 全绿
[ ] ./gradlew.bat :app:assembleRelease 出包并真机安装验证
```

## 六、一句话总结

- **版本号**：应用版本只认 `build.gradle.kts`；schema 只认 `Db.VERSION`；导出格式只认 `ChatArchive.SCHEMA`；依赖只认 `libs.versions.toml`。
- **参数**：需要不改代码就能变的 → `AppSettings`（四处齐改）；只影响一个领域的 → 该模块的 `companion object`；两者之间必须有夹紧层。
- **改完必须**：DB 升级两条路径都过、`KEY_*` 只增不改、有静默失效风险的常量补测试。
